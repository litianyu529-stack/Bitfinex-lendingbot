# SAFE 状态与恢复

SAFE 的目标是停止不确定写入，而不是自动猜测交易所发生了什么。

## 进入 SAFE 的典型原因

- 钱包可用余额未知或账户同步失败；
- 市场行情过期，或稳健锚点不足两个有效信号；
- SUBMIT/CANCEL 请求可能已到达交易所，但客户端没有得到可判定结果；
- 已确认的提交响应缺少可持久化 Offer ID；
- 进程启动时发现未完成的执行意图。

进入 SAFE 后不创建、不撤销、不重试交易写入。V3/V4 LIVE 锁也不能替代 SAFE 恢复证据。

## 未知提交

V4 使用金额、利率、期限、创建时间和唯一匹配条件在权威 Offers 中查找候选。只有同一 Offer ID 在两次至少相隔 30 秒的快照中保持唯一匹配，才绑定到原意图。零个或多个候选都继续 SAFE。

## 未知撤单

V4 已知具体 Offer ID。只有两次至少相隔 30 秒的权威快照都确认该 ID 消失，才将取消意图标为确认。

## 恢复模式

两次证据一致、且没有 `SUBMITTING/AMBIGUOUS` 意图后：

- SAFE 前为 SHADOW/PAUSED：恢复到此前模式；
- SAFE 前为 LIVE：恢复到 PAUSED，必须重新完成人工 LIVE 确认。

不要手工删除 SQLite 意图来“解除” SAFE。应先在 Bitfinex 页面核对钱包、Offers 和 Credits，再保留日志与数据库副本进行调查。

## 明确拒绝

HTTP 或 API 明确拒绝不会被当成“结果未知”。意图记为 `REJECTED`，原 Offer（如有）保持可见，事件写入本地数据库。连续的权限、参数或余额拒绝应由人工修复配置，而不是提高自动重试频率。
